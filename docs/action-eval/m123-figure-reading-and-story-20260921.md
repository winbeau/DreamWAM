# M1–M3：读图与实验叙述

依据：2026-09-21 的真实 checkpoint trace、模型 `7300f34` / evaluator
`e5a5cc5` 的五对 Spatial pilot，以及[完整证据记录](m1-m2-m3-goal-20260921.md)。
本文解释已有结果并提出后续验证；不新增实验或改变原始结果。

## 黑色需要按图的类型解释

| 图的位置 | 黑色或深色表示什么 | 怎样区分 |
|---|---|---|
| 原始 RGB、patch 裁剪 | 图像本身较暗 | 不表示注意力或是否计算 |
| 左列 Router probe AV | 该动作 query 对该视觉 key 的注意力为零或很小 | 这里不是用黑色标记被剪掉的 token |
| 中列 Executed AV，没有蓝框 | 该 key 未参与本次实际注意力，绘图代码补零 | 不应解释成模型计算后认为它不重要 |
| 中列 Executed AV，有蓝框 | key 确实被读取，但显示的注意力很小或为零 | “读取过”和“权重大”是两个问题 |
| 右列 VV backward support | 该位置得到的加权 VV 支撑为零或很小 | 可能来自可见性 mask，不能直接推断没有用 |
| execution-and-cache-age 顶部更新图 | 该步没有重算这个视觉 query | 黄色表示重算 |
| execution-and-cache-age 中部保留图 | 该步结束后没有保留这个视觉 key | 这是保留状态，不是逐次实际读取记录 |
| execution-and-cache-age 底部年龄图 | 年龄接近零，即刚更新 | 此处深色恰好表示“新”，亮色表示更旧 |

第一行热力图还叠加了 RGB 底图，肉眼观察的深浅也受原图影响。
中列当前把未读取 token 补零，导致它与接近零的已读取注意力使用相同颜色。
读图必须结合蓝框；改版图例应把“未读取”“mask 禁止”“有效低数值”分开编码。
不同文件的色标会变化，VV 与 AV 也使用不同色标，不能只凭颜色跨图比较。

前面核对的 H100 adaptive / task 1 / init 1 / chunk 6 例图，AV 种子均在
首帧。模型 mask 禁止首帧视觉 query 读取未来帧，因此未来两帧的 VV 支撑
严格为零。这解释了右下两块全黑；不等于未来 latent 没被计算或没有作用。

## 蓝框、绿色加号与青色圆圈

- **蓝框**：实际执行的注意力读取了这个视觉 key。
- **绿色 `+`**：本去噪步选中这个视觉 token 作为 query 重算；对应更新视觉表示。
  它与文件名 `q0` 不同：`q0` 是动作分支的第 0 个 query。
- **青色 `○`**：AV 聚合分数选出的种子，供下一步沿 VV 依赖寻找支撑 token。
  它不是最终保留集合，也不是最终重算集合。

例如某格有蓝框但没有 `+`，表示本步仍读取它的缓存表示；某格同时有蓝框和
`+`，表示本步更新并读取。圆圈来自所有 head / action query 的聚合，所以
不一定落在单个 `h0-q0` 图最亮的格子上。右列 VV 也是聚合支撑分数，不能
当成 head 0 / query 0 单独对应的 VV 注意力。

`s00` 必须 Dense，蓝框和加号全覆盖是预期行为。Q/KV 标题给的是 Sparse
配额，并不限制这个 Dense 首步。看稀疏选择应结合同一 chunk 的
`inputs-and-token-ids.png`、`s05-l00-mean-heads-queries.png`、
`execution-and-cache-age.png`，先确认该 chunk 的第 5 步实际执行哪种操作。

## 可以检验的研究主线

目标叙述是：**根据机器人当前观测分配视觉计算预算，在动作需要的视觉信息
及其依赖上保留读取能力，并选择必要的去噪步更新表示。**

| 模块 | 要回答的问题 | 需要展示的证据 |
|---|---|---|
| M1 | 这个 chunk 应花多少总计算？ | RGB/状态历史 → 预算 → 实际总重算、总读取与延迟 |
| M2 | 预算内应读哪些 token、更新哪些 token？ | AV 种子、VV 支撑、实际读取与更新集合及坐标对应 |
| M3 | 哪些去噪步需要更新？ | Dense/Sparse/Reuse 时间轴、表示年龄与实际工作量 |

“重要”与“需要重算”不能混为一谈：一个对动作重要但没有变化的 token 可以
继续读取其缓存表示。蓝框与加号分开，正是为了展示这一区别。AV/VV 在这里
是选择代理信号；热力图本身不能证明因果重要性。

结果宜按以下顺序组织：

1. **提出冗余假设**：chunk 之间和去噪步之间的更新需求可能不同。需要通过
   干预或预算扫描验证，不能仅凭看起来静止就判定任务容易。
2. **展示预算如何执行**：用同一条轨迹依次串起真实输入、预算曲线、patch
   选择和逐步路由，保留 task / init / chunk / step / layer / token ID。
3. **证明每个模块的增量作用**：M1 对比相同总体预算的固定分配；M2 在相同
   实际重算/读取预算下对比 uniform、random、AV-only、AV+VV；M3 对比固定
   调度与自适应调度。都要计入探针和调度成本。
4. **最后展示系统收益**：完整 predict_action 延迟、闭环 SR 和误差/失败案例。
   在独占 GPU 上用相同输入交替计时；小规模开发筛查与独立确认结果分开。

## 这轮结果现在能支持什么

已验证预算控制、token 路由、Dense/Sparse/Reuse 和真实执行追踪能够运行。
候选闭环共 114 个 chunk，预算为 high / medium / low = **31 / 11 / 72**；
实际 Dense / Sparse / Reuse 步数为 **114 / 641 / 385**。

但系统收益尚未成立：五对 pilot 为 Dense **5/5**、候选 **3/5**，双方无
评测错误，五对初始 RGB/状态逐字节一致。共享 GPU、不同闭环轨迹下的 warm
推理均值是 **328.599 / 321.672 ms，约 1.022×**，不是独占同输入加速结果。
这些数字不支持“高加速且保持成功率”的结论。

有两处值得进入下一轮假设检验：

- **预算接口还需对齐原意。** M1 目前控制每次 Sparse 的 Q/KV 配额，而 M3
  的 chunk 总额外重算上限固定。低配额会允许更多 Sparse 步；本轮低/中/高
  预算的平均重算 token-layer 数为 15,120 / 15,900 / 16,830，差异远小于
  单步配额的 10% / 20% / 30%。不能把单步稀疏比例当作 chunk 总预算。
- **低变化不一定表示低难度。** 两个失败 episode 分别有 35/40、34/40 个
  chunk 使用低预算。可能是低预算影响控制，也可能是任务先卡住、观测变化
  随后变小；目前不能判定方向。需固定 M2/M3、恢复预算或回放匹配输入来检验。

适合目前汇报的一段话：

> 我们实现了从观测预算、动作引导的视觉依赖选择到去噪步调度的可追踪执行
> 原型，并验证可视化与真实执行对应。初步闭环测试暴露出预算接口和代理
> 信号的局限：单步配额不等于整 chunk 成本，观测变化小也不等于任务容易。
> 当前五对测试出现两次成功率回退，共享运行的推理收益约 1.02×。下一步需
> 先修正预算接口，再用等预算消融及独占同输入计时验证各模块的实际贡献。

这是一条有完整证据的开发与诊断叙述；将来能否成为有效方法的结果叙述，
取决于后续质量和性能验证，而不是热力图看起来是否集中在物体上。
